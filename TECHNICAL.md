# Overlay Kit — technical reference

For installation and the user-facing overview, start with [README.md](README.md). This reference preserves the detailed development and verification notes; dated sections describe the state at their recorded checkpoint.

A **small composable browser-overlay foundation** for an emote wall, configurable chat overlay, avatar scene, and event alerts. Independent of Stagehand, SketchyChat and OBS-specific controllers.

**Status (2026-11-22):** The standalone Chatbus live relay combines Twitch, Kick, YouTube Live Chat and TikTok LIVE sources into one normalized overlay stream. Anonymous Twitch IRC is connected with a complete emote catalog; Kick's negotiated web realtime transport delivers normalized Kick messages and native emotes. YouTube now prefers Chatbus's official Live Chat API when a server-side API key or OAuth access token exists, and otherwise uses the optional read-only public InnerTube reader from Node. The public reader uses unsupported YouTube web endpoints and may break or be rate-limited; on 2026-11-22 a real no-credentials live message crossed the local HTTP/WebSocket relay into a normalized Overlay Kit message. A credentialed official live handshake has not been independently verified here. The default Twitch and Kick paths remain read-only public transports; a locally signed-in Twitch account additionally uses Chatbus's authenticated EventSub chat connector, while Kick chat remains anonymous web realtime rather than the official Kick chat-read API. TikTok uses Chatbus’s opt-in Node-hosted read-only connector; simultaneous local TikTok + Kick delivery is live-verified. Native OBS CEF remains untested.

**Extracted game:** Emote Pusher now lives in the independent sibling project at ../emote-pusher/, with its own ChatBus transport, browser-source URL, game controls, physics, and tests. Overlay Kit no longer ships its cabinet, fifth tab, or game settings. See the sibling README for how to run it. Prior browser settings are preserved in an origin-local migration archive.

## Run

Requires pnpm, Node 24 and no Docker. Chatbus is consumed as the tracked, pinned runtime snapshot in `vendor/chatbus` (`file:vendor/chatbus` in package.json, with the exact upstream commit in `vendor/chatbus/UPSTREAM_COMMIT`); no sibling checkout or registry token is required to install. To work against a live ../chatbus checkout during development, point that dependency at it temporarily.

    pnpm install
    pnpm test
    pnpm dev

`pnpm dev` starts the normal development host: Vite/HMR plus the local live Chatbus backend behind the same browser origin. It defaults to **http://127.0.0.1:5173/**; set `OVERLAY_DEV_PORT=5178` (or another free loopback port) when a fixed project port is useful. The backend uses an internal loopback port and Vite proxies `/api/live`, `/api/oauth`, `/api/fonts`, and the read-only `/live` WebSocket, so editor controls and live sources keep working while HMR remains active.

For the built standalone relay instead, run `pnpm live`; it builds first and serves the production-style pages from **http://127.0.0.1:5219/**. In the top live-source field, click the platform logo to choose **Twitch**, **Kick**, **YouTube** or **TikTok** from the named logo menu, enter the channel indicated by the platform-specific placeholder, then use the embedded link icon on the right (or Enter) to add it. Repeat to combine sources; selecting an active source changes the icon to unlink so only that source is removed. Each active logo-and-channel chip shows its own connection, emote and badge readiness icons. Click a chip to restore its source field and open the Reconnect / Disconnect menu; either action targets that source only. A local reconnect restarts that provider; hosted reconnect replaces this editor’s subscriptions without forcibly restarting a shared upstream room. Do not confuse "connecting" with a joined channel. Wall, Chat, Avatars and Events source URLs live on the same host. Hover each workspace tab and choose Copy link to copy its complete OBS URL.

Chatbus currently exports TypeScript source rather than emitted declarations. Overlay Kit retains the strict TypeScript compiler, but aligns its optional-property/index and unused-symbol flags with Chatbus's own tsconfig so importing this actual local dependency does not falsely type-check the dependency under a different project's stricter settings. Chatbus still passes its own independent typecheck. The exact runtime snapshot is shared with Noita and Sketchy; changes originate in the upstream Chatbus repository. Recent Kick history is marked replay, not live. See [live verification](docs/kick-official-oauth.md#shared-transport-unification-2026-11-17).

The control room is **not required to remain open**. One Node relay owns the active Chatbus source set, fans normalized messages/moderation events to independent WebSocket browser clients, and restores the selected `[{platform, channel}, ...]` set on server restart via an ignored local `.live-channel.json` file. Message IDs are namespaced by source and moderation/clear events are source-scoped, so overlapping provider IDs cannot delete another service's rows. The relay binds **127.0.0.1 only**; remote viewers cannot reach it unless you explicitly proxy/forward ports. Stop the server to end its connections.

To run the **preview-only** raw Vite editor with no local Chatbus relay/API:

    pnpm dev:vite

The generated dist-demo/ has five HTML pages and local SVG sample artwork. The editor also learns actual Chatbus emote/badge/7TV paint visuals for synthetic previews using a bounded, clearable, origin-local cache; it stores neither real chat text nor chat/user IDs. Public avatar asset URLs may still identify an account. See [Preview cosmetics cache](docs/preview-cosmetic-cache.md). Independent browser sources start empty until genuine Chatbus events or explicit synthetic tests arrive. preview=1 enables sample fixtures only in the editor. Chat/Wall/Avatars local preview buttons use BroadcastChannel, while Events test notifications are sent only to the Events preview iframe; live clients use the server WebSocket. Never paste secrets into channel names or source URLs.

**TikTok LIVE:** no account sign-in is needed for the tested anonymous public
stream path. The TikTok option appears when the local server supports it.
The exact MIT-licensed connector 2.4.0 runs only on the server and uses
an unofficial external signing service. Gift alerts report gift counts,
not inferred monetary amounts. Native TikTok emotes and badge artwork
are not implemented. Hosted TikTok is enabled by default in the same bounded
room path, subject to signing-service availability and usage limits.
Hosts can explicitly disable it with `OVERLAY_HOSTED_TIKTOK=0`.
See [TikTok multiplatform integration](docs/tiktok-multiplatform.md)
for live receipts, configuration, and deployment boundaries.

You can override the listening port: `OVERLAY_PORT=5220 pnpm live`. YouTube Live Chat accepts public video IDs/URLs without credentials through the Node-only unofficial reader. Set `OVERLAY_YOUTUBE_API_KEY` or `OVERLAY_YOUTUBE_ACCESS_TOKEN` to use the official API instead; server credentials are never placed in browser-source URLs or localStorage. Set `OVERLAY_YOUTUBE_PUBLIC=0` to disable credential-free fallback. The unofficial reader is not guaranteed to return moderation and membership events with the same coverage as the official API. If running under OBS on the same workstation, point OBS browser sources at this loopback host; actual OBS CEF behavior is **not yet independently verified**.

## Implemented

**Current artwork policy (2026-11-26):** Historical descriptions of bundled Kick role SVGs and the exact Kick wordmark below are superseded by [optional personal artwork](docs/kick-badges.md). Chatbus's shared badge catalog now retrieves the four named SVG definitions from Kick’s public website assets during connection, with optional personal PNGs and semantic labels as fallbacks. No copied role assets are tracked. See [automatic role artwork](docs/kick-badges.md#automatic-role-artwork-connection-time).

- **Scene:** src/scene.ts manages unique IDs, maximum active items, overflow policies, expiry, dynamic configuration and cleanup; timer clock is injectable for tests. No unbounded frame loops or network calls.
- **Chatbus adapter:** src/chatbus.ts accepts normalized Chatbus fragments and retains emote base art, zero-width layers and modifier metadata. Standalone modifier art and native cheermotes are represented, too. No transport dependency or provider fetch.
- **Safe DOM renderers:** src/renderers.ts uses textContent instead of innerHTML, rejects non-http(s) emote image URLs, renders emote stacks, user badges and a compact per-message Twitch/Kick/YouTube/TikTok service badge, and accepts basic size/visibility controls.
- **Four views:** src/views.ts uses the same scene to run chat feed and emote wall; src/avatar-scene.ts owns the single-canvas avatar simulation; src/events.ts owns the independent social-signal alert queue. Consumers can inject custom renderMessage or renderArtwork functions, returning optional dispose() to stop GSAP timelines, Matter bodies, listeners etc.
- **Preview cosmetics:** src/preview-asset-cache.ts stores bounded, sanitized artwork and 7TV paint metadata from the existing live Chatbus listener, so the fictional sample messages exercise actual upstream-resolved images and styles between editor sessions. When no genuine paint has been captured, two explicit synthetic-only paint fixtures cover gradients and stacked layers. The editor shows counts and provides Clear cached art. See [Preview cosmetics cache](docs/preview-cosmetic-cache.md).
- **Chat and Emote Wall triggers:** Opt-in staff-command and provider channel-event rules can temporarily launch bounded visual cues or existing local style/motion packs, with cooldown, replay protection and automatic restoration. See [Overlay Triggers](docs/overlay-triggers.md).
- **Twitch subscriber GIFs:** Chatbus interprets Twitch IRC GIF tags and preserves their full GIPHY URLs. Chat renders GIF media; Wall optionally floats them under Wall → Artwork → Twitch subscriber GIFs (off by default). See [Twitch subscriber GIFs](docs/twitch-subscriber-gifs.md).
- **Preview bridge:** src/bridge.ts uses same-origin BroadcastChannel for editor-driven preview and validates nested messages. It is neither authenticated nor an external Twitch transport.
- **Control room + browser sources:** demo/ and five HTML entry pages support configurable motion, font/emote size, TTL, max items, badge/name visibility, explicit sample bursts and same-origin event delivery. Motion paths include still, float, bounce, burst, orbit, sway, flutter and opt-in collision.

One Chatbus message can appear as a single chat row and multiple independently tracked emote-wall entities; zero-width overlay images remain in the correct base artwork.

**Emote Chorus (opt-in):** Wall → Movement → Emote chorus reactions (`?chorus=1`) watches normalized emotes from three distinct, identifiable viewers within eight seconds. After a 12-second per-emote cooldown, a chorus adds at most six bounded `pop` emote entities to the existing scene, without synthesizing chat messages or changing Chatbus. The detector is session-local, deduplicates message IDs, caps tracking state, resets on channel switches and chat clear, and removes contributors on moderation events. Triggered artwork is tied to the triggering message ID, so deletion/user-clear removes it too. The default is off and Chat is unaffected. A standalone `createEmoteChorusDetector` helper permits custom host-side integration. This is separate from EmoteWall's configurable threshold-and-kappagen feature set.

## Live Chatbus connection and boundaries

- **Real runtime:** `server/hub.ts` uses the pinned Chatbus package and selects a provider transport per source. Twitch defaults to Chatbus's anonymous IRC adapter; when a local Twitch account is connected, `server/http.ts` routes Twitch through Chatbus's authenticated EventSub chat connector. Twitch's supported primary rich API is authenticated EventSub, so IRC must not be treated as complete moderation/event coverage. Hosted Vercel Twitch rooms use the anonymous IRC path. Kick uses Chatbus's current anonymous web-realtime negotiation: it resolves Kick's offered provider, currently Centrifugo, mints a guest token, subscribes the channel/chatroom feeds and can fall back to dynamically negotiated Pusher credentials. Kick's web realtime endpoints are undocumented and are not the official Kick Public API. YouTube uses Chatbus's official Live Chat API connector with a server-side API key or OAuth token. `createLiveMixer` owns any number of independently lifecycle-managed `{platform, channel}` children and forwards one normalized presentation stream.
- **Independent source transport:** server/http.ts serves the actual static UI, binds loopback, enforces same-origin Origin checks on read-only /live WebSockets and on POST /api/live/connect, /api/live/reconnect and /api/live/disconnect, rejects overly large browser commands and serves only dist-demo public assets. No chat provider tokens or raw provider payloads reach the output. Multiple source pages see the same combined source set without keeping the editor open. On runtime reconnection the WebSocket source client retries with a bounded backoff.
- **Moderation:** message delete, whole-chat clear and per-user timeout/ban clear Chat, Emote Wall and viewer avatars using the source that originated the event. Individual Chat deletes detach original content immediately, then optionally animate a content-free Scribble or Crumple afterimage; Emote Wall moderation remains immediate. Source-scoped IDs/usernames travel through the safe presentation projection, so one service cannot clear another service's matching IDs. The local relay retains a bounded projected message snapshot and replays it to newly connected browser clients, so a source opened after messages arrived can receive recent chat immediately; that replay is bounded and respects moderation/clears. This does not provide an arbitrary historical backlog.
- **Emotes:** third-party BTTV, FFZ and 7TV catalogs are loaded by Chatbus and used by its normalized fragments; native Twitch emote tags also work. The foundation preserves zero-width attachments and handles the documented FFZ modifier flags: Hidden suppresses overlay layers, while FlipX/FlipY, GrowX, Rainbow, HyperRed/HyperShake, Cursed, Jam and Bounce compose as visual effects. Effects compose on the complete emote stack without replacing wall material/color/edge treatments or stretching normal emotes. Unknown flags remain in metadata but do not invent effects. The bundled OBS pages load `src/ffz-effects.css`; external consumers must import the exported `@myrqyry/overlay-kit/ffz-effects.css`. Reduced-motion preference disables repeating effects. Provider failures surface as degraded state, not a fabricated success.
- **Kick native v2 badges:** Chatbus now reads sender `badges_v2` for verified Kick-hosted badge images (Flyby, GoldenK, GOAT and future cosmetics), with source ordering and selection. Kick level badges also include image URLs even when `selected:false`; the website displays them as inline SVG, while OverlayKit uses the hosted PNG. No global cosmetic URL list is hardcoded.
- **Native Kick subscriber + gifter badges:** Kick chat identity exposes semantic `subscriber` and `sub_gifter` refs with counts. Overlay Kit now renders those immediately as compact `SUB N` / `GIFT N` role badges instead of dropping them when no artwork URL exists. Chatbus still resolves subscriber counts to the highest channel-specific image milestone supplied by Kick's public (undocumented) channel JSON; when that real subscriber art arrives it replaces only the `SUB N` fallback in-place without restarting the message, while the gifter role remains visible. No guessed Kick artwork is invented for roles without verified images.
- **Kick role artwork:** When Chatbus actually reports Kick moderator or verified identity refs, OverlayKit now renders the exact local SVG assets supplied from Kick’s UI. A `sub_gifter` count of exactly 1 or 25 uses the supplied `Gift1` or `Gift25` icon, respectively, while other counts keep their `GIFT N` labels until corresponding artwork is verified. Authentic native image-backed badges take precedence. These are chatter identity badges, separate from the Twitch/Kick streamer source portraits.
- **Kick recent chat on load:** Overlay Kit opts into Chatbus's bounded recent-chat snapshot from Kick's current web-client endpoint, then hands off to realtime with message-ID dedupe. The local relay retains the current projected message snapshot, so a browser/OBS source that connects after the server has already restored a channel still receives recent chat immediately. The history endpoint is internal/undocumented; if it fails, realtime chat remains usable.
- **Native Twitch badges:** anonymous IRC provides set/version references; the server uses the public IVR global/channel catalogs and Chatbus's resolveBadgeRefs matcher to produce accurate role, subscriber and other native Twitch badge images. Channel-specific versions win, unknown versions remain absent rather than invented. The old unauthenticated Twitch badge endpoint was shut down in 2023 and Helix requires Twitch OAuth; IVR is an optional third-party mirror, not an official API. Badge fetching is timed, bounded, cached for 15 minutes, cooled down after failures, and CDN URLs are validated. Badge catalog state displays independently as ready/loading/degraded. Chat does not stop if badge lookup fails.
- **Twitch streamer portraits for multichat:** Each Twitch source independently resolves its channel owner's profile image through Chatbus's cached public-identity lookup. The portrait renders as a small circular source badge beside the existing Twitch service icon, separate from the chatter's moderation badges. It arrives asynchronously: messages are never delayed, existing visible rows receive an in-place badge update, new messages inherit the source portrait, and replayed rows retain late updates. The existing Chat Display badges setting controls visibility. Failed or stale lookups leave the existing service icon alone; YouTube is unchanged. IVR's user identity endpoint is unofficial, unlike the OAuth-protected Helix alternative.
- **MingCute visual cues in the control room:** The editor uses the already-bundled MingCute Core Regular icons for collapsible settings sections, each independent badge category, inspector search, and connection/emote/badge readiness; the existing workspace tabs and toolbar use the same icon family. Six restrained semantic accent tones distinguish control groups and indicate whether badge types are enabled, while the Twitch/Kick/YouTube/TikTok source chips retain their platform colors. Glyphs accompany persistent labels, full status tooltips and accessible control names; reduced-motion preferences are respected. These are **editor-only** decorations and do not alter chat output, preset values, network providers or OBS rendering.
- **7TV-painted message outlines:** Chat **Message outline** (0–8px) can follow the same sanitized 7TV solid colors, gradients, legacy gradient functions and ordered v4 paint layers as usernames, including rounded corners. Paint borders work independently of Theme/User color/Name paint fill selection and retain their color with transparent fills; flat paints render as native rounded strokes while real gradient/image artwork retains its masked layers; the renderer does not execute provider-supplied CSS. Missing paints continue to use the previous outline fallback. Late cosmetic updates and view hot-settings changes update the existing message, without a new chat transport. See [7TV name paints](docs/name-paints.md).
- **Per-type Chat badge controls:** The editor's **Chat → Badges** section exposes the existing master display switch plus independent controls for platform logos, streamer/source portraits, Twitch chatter portraits, moderator/VIP/verified/other roles, subscriber/founder badges, gift-subscription gifter badges, and 7TV/BTTV/FFZ/Kick cosmetics. Everything remains visible by default. Platform logos retain their own switch (as before, the master badge switch does not hide the platform logo). Changes flow through existing preview messages, saved per-view presets, and OBS source URL parameters without mutating the raw Chatbus badges. Late identity updates honor the same visibility settings, and re-enabling a category restores its existing pictures without reconnecting chat. Native Twitch badge metadata now retains provider and ID so the groups are based on identity, not translated names.
- **User-color portrait rings:** Streamer/source and individual chatter avatar badges use thin, round outlines in each owner's actual chat-name color. Twitch source color comes from the same cached public profile lookup as its portrait (no extra request); a channel owner's live chat color takes precedence when observed. Individual Twitch chatter portraits use the message author's normalized color; Kick stream owners use their color when supplied by the broadcaster's chat event. Unknown or invalid colors preserve the former neutral ring, never another chatter's color. Other provider, subscriber and cosmetic badges are unchanged. The ring is a subtle .07em CSS shadow and follows live badge patches, replay and hot appearance changes without changing settings or chat transport.
- **Twitch chatter profile pictures:** Unlike the channel-owner source portrait, individual Twitch IRC chatters have login names but no embedded profile-image URL. The relay now performs bounded background lookups through Chatbus's validated public Twitch identity resolver, adding a separate circular `twitch-user` image beside the `twitch-source` icon and native Twitch role badges. Requests are limited to three concurrent per source with a short queue, deduplicated by login and cached; unsupported, stale, or failed lookups never delay a message or resurrect deleted rows. Existing visible rows receive keyed badge patches and the live replay retains those updates. The Chat badge controls (master switch and per-type toggles) govern these compact images. The IVR mirror is unofficial; this is not a guaranteed avatar for every viewer or a verified Twitch Helix API feature.
- **Kick streamer portraits for multichat:** Each Kick source now independently resolves the channel owner's `user.profile_pic` from the web-client `/api/v2/channels/<slug>` response using Chatbus's cached, validated avatar lookup. The supplied `files.kick.com` image becomes a small circular Kick source badge, alongside the platform icon and without overwriting the chatter's native/subscriber badges. It loads asynchronously, patches still-visible messages, persists through replay, is scoped by source, and is hidden by the existing Display badges toggle. Failed or missing images leave chat unchanged; Twitch remains supported. This is an undocumented Kick web endpoint, not the official public API.
- **Late-arriving badges:** chat messages display immediately, even when the badge catalog is loading. Once resolved, the relay sends a keyed badge update so existing rows gain their icon without resetting their lifetime/animation or reappearing after moderation. The emote wall ignores cosmetic badge updates. Pending badge updates are bounded and cleared on moderation and channel changes. Additional BTTV/FFZ/7TV user-specific supporter badges remain a separate enhancement.
- **Integration contract:** `fromChatbusEvent(event)` adapts *actual* Chatbus `ChatEvent`, retaining only safe display data; `applyLiveEvent` feeds the presentation consumers. Hosts such as Stagehand can import the same adapter instead of adding their own parser. Twitch, Kick, YouTube Live Chat and TikTok LIVE are enabled in this relay; a locally signed-in Twitch account additionally uses Chatbus's authenticated EventSub chat connector. Hosted Vercel Twitch rooms remain on the anonymous IRC path.
- **OBS boundary:** Chrome browser-source simulation, local static server and independent WebSockets are verified, but actual OBS embedded CEF has not been tested. Unlike BroadcastChannel, the WebSocket relay does not rely on a shared browser partition. Do not publish the unauthenticated local control endpoint on the Internet or use the local server as a public hosted service.

In preview-only development (`pnpm dev:vite`) without the live relay, preview mode remains available and clearly labels its generated messages as synthetic.

**Preview defaults:** Emote Wall and Chat are enabled on first visit; Avatars and Events start disabled to avoid mounting unnecessary previews. Each can be enabled from its workspace switch, and saved enabled/disabled choices take precedence.
In the studio, synthetic preview fixtures remain visible after a live transport connects and are replaced only when the first real live message/event arrives. This keeps quiet or offline channels from turning the preview blank; if all live sources later disconnect, the preview fixtures return.

## The options system: from minimal to genuinely configurable

The editor has **103 validated, directly wired options** derived from one TypeScript manifest in src/options.ts. The editor is a compact, desktop-style workspace. **Emote Wall**, **Chat**, **Avatars**, and **Events** are top-level tabs in the application chrome, not buttons hidden inside the sidebar. Each tab gets a dedicated main 16:9 preview canvas with its own scoped settings in a left inspector; each view has independent settings; Chat separates **Layout**, **Styling**, and **Animations** instead of mixing appearance and motion in one group; Styling includes an optional **Exit edge fade** with six profiles, pixel or percent distance, edge opacity, hold, terrace steps, and optional patterned transparency (Pixel dither, Scattered grain, Torn paper), automatically following the side older chat leaves from, chat and wall keep separate lifetime/capacity/artwork controls, and avatars have population/size/behavior controls. Enabled inactive previews remain mounted and receive events. Hover a workspace tab (tap on touch, or press Down arrow when focused) to reveal its **Enabled** switch and **Copy link** action. Turning Enabled off unloads that preview, including its rendering and live subscriptions, and persists the choice in the browser. The optional **Compare** control shows only enabled previews; changing tabs itself never reloads them. All applicable settings for the active tab are available, and search stays scoped to that editor; the New line after username toggle is hidden when Floating label makes it inapplicable, without deleting its saved value. Chat has 65 controls, Wall has 18, Avatars has 5, and Events has 15, with no shared controls; there are 103 unique validated options. Category groups can collapse independently. The active editor tab survives reloads, and left/right arrow keys move between accessible workspace tabs. The editor is **viewport-locked**: the document itself never scrolls and preview canvases preserve a 16:9 aspect ratio while resizing to the available stage. On desktop the left inspector alone scrolls; the main preview and top tabs stay in place. On narrow screens the preview and settings are **two separate viewport-filling panels** selected using the Settings / Preview buttons, so users do not need to scroll through controls to reach the canvas. Compare mode fits inside that same window. The original Chat and Wall OBS source pages remain available; Avatars and Events add a third and fourth source.

- **Admission filters:** Chat, Emote Wall and Avatars each have an independent bounded comma-separated ignored-username list. Matching is exact and case-insensitive after normalizing an optional `@`; ignored messages never enter the scene or trigger Wall Chorus. The same admission path is used by live input and Studio preview fixtures.
- **Chat capacity/artwork:** independent chat message limit, lifetime and emote height.
- **Unicode emoji artwork services:** Chat can render native system emoji (including Apple on supported Apple hosts), Google's Noto Color Emoji, Twemoji or OpenMoji; Emote Wall optionally admits Unicode emoji as artwork (off by default), independent of Twitch/Kick/7TV/BTTV/FFZ emotes. Settings are isolated per view, persist in presets and OBS source URLs, fall back to native glyphs on artwork failure, and never load provider scripts. See [Emoji services](docs/emoji-services.md).
- **Wall capacity/artwork:** separate wall item limit, lifetime and emote height.
- **Independent text typography and color source:** Chat → Typography retains the old `font`/message-size setting (now labeled **Message text size**), and adds **Username size** (0 = Match, otherwise an independent pixel size shared by the username and all platform/role/cosmetic/avatar badges) and **Message text color source** (Theme, User color, Name paint). Theme preserves the style pack's text color. User color applies each chatter's validated chat color to the **message text**, without recoloring their username or emotes. Name paint uses bounded, sanitized 7TV paint layers/gradients as CSS text-clipped lettering; non-image v4 layer opacity is composited into gradient/solid colors, while unavailable or unsafe paints fall back to user color or the theme. The selected color applies to the real message lettering rather than duplicating message DOM. Late 7TV identity updates and appearance changes update the existing live row without altering timers, moderation, emotes, or OBS transport. Both options roundtrip through per-view presets and OBS source URLs and default to the previous appearance.
- **Painted username shadow isolation:** OverlayKit's own **Chat → Typography → Text shadow** continues applying to ordinary usernames and message text, but no longer inherits into validated 7TV-painted usernames or their independent text-clipped layers. This prevents the dark OverlayKit shadow from muddying the bright paint fill. Any text/drop-shadow explicitly encoded in the 7TV paint is retained, and reverting to an unpainted username restores the selected normal text shadow.
- **Name-paint-only background blur:** **Chat → Styling → Name paint background blur** is visible only when **Message background source → Name paint** is selected. Its 0–48px radius (0 is the default) uses one native CSS blur for the combined background paint layers, skipping the filter entirely for solid-only or invisible-detail fills inside an overscanned, rounded clipped group, not the username, message text, emotes, bubble outline or scene behind the message. It persists in OBS URLs as `messagePaintBlur`, follows the existing message-background opacity, and is safe to change on visible rows without resetting their lifetimes.
- **Per-bubble maximum width:** **Chat → Layout → Max message width** limits individual bubble width to 0–1920px; 0 preserves the existing layout and avoids changing saved sources. Positive caps preserve separate username/message alignment, wrap text naturally (including in Horizontal Strip), and remain effective in Stack, Latest Only, and Floating label modes. The editor and OBS URLs store this as `maxMessageWidth`; it does not resize Emote Wall. **Uniform message width**, directly below the maximum, stretches short bubbles to the same effective width as long ones. It defaults off, only takes effect with a positive maximum, and respects canvas padding plus the existing Horizontal Strip and Latest Only limits. The separate text/bubble alignments, floating labels and existing messages are preserved. The preference roundtrips in chat presets and OBS URLs as `uniformMessageWidth=1`.
- **Overlay-friendly link display:** **Chat → Content → Link display** offers Compact (default), Domain only, Hide URL (show `↗ link`), and Full. Compact represents URLs as `↗ youtube.com/watch` or `↗ clips.twitch.tv/ClipId`, dropping noisy query strings from the **visible** text. Full preserves the original displayed text. Every shortened token keeps its raw source URL in safe DOM metadata, but browser-source chat has no clickable links or remote previews. The rendering is DOM/text-only (no `innerHTML`); it recognizes HTTP(S) and `www.` links, leaves emails, invalid links, emotes, and URL-contained `@handles` alone, and caps substitutions per message. The selected choice roundtrips through presets and OBS URLs as `links` without changing Chatbus's source fragments.
- **Context-aware animation timing:** In **Chat → Animations**, the existing Message entrance duration is hidden when Message entrance is None; a new **Letter entrance duration** slider sits directly below Letter entrance and is hidden when its effect is None. Message and letter timing are independent (both 120–1200ms, defaults 320ms), including JavaScript-driven Scramble and CSS letter motion. **Movement duration** hides while Smooth message movement is disabled. Hidden controls keep their values in local presets and OBS URLs; older presets/links without a letter-specific timing inherit the formerly shared `enterMs` value to preserve previous animations. Letter entrance text now correctly explains that glyph and message entrances can run together.
- **Composed message and letter entrances:** An earlier CSS override deliberately disabled the entire message entrance when per-letter motion was active. That override is removed: message bubbles now run their selected entrance independently while letters animate within them, including Pop + letter Rise, Slide-right + letter Fade, and Scale + Scramble. Long messages beyond the bounded per-letter budget still keep the message entrance. Existing exit and reduced-motion rules are unchanged.
- **Chat mentions use target colors:** Both Chatbus's structured mention fragments (including Twitch user IDs) and literal `@username` tokens in ordinary Kick/chat text use the *mentioned* user's actually observed, validated chat-name color. The feed maintains a bounded per-source identity-color map; it never guesses missing colors or borrows the same username's color from another source. Unresolved mentions look like normal text and gain color in place if the named user later speaks; a changed color likewise updates still-visible mentions without replacing messages or resetting expiry/animations. The normalized source fragments and emotes are unchanged; URLs/emails are never treated as mentions (shortened overlay link labels intentionally affect visible/copied display text, with the complete URL retained in token metadata and recoverable through Full mode). The mentioned color overrides the author's selected Theme/User color/7TV Name paint **for that mention alone**. Source removal, chat clears and targeted moderation release observed identity colors. This is automatic presentation behavior, not a new provider connection, API lookup or saved setting.
- **Restored username line breaks:** **Chat → Layout → Username location → New line after username** now switches between the existing two-line presentation (default/on) and a flowing single-line message (off: service icons, badges, username and message on the same line, wrapping as necessary). The existing identity and body elements are reused, along with all chat layout modes, animations, badge/paint updates and message lifetime. The toggle sits immediately below Username location and is hidden when Floating label is selected; the floating border label always requires its own header, and the previous toggle choice survives switching back to Inline. ## Google Fonts in Chat (2026-10-18)

The **Chat → Typography → Google Font** control browses a locally bundled searchable index of **1,950 real font families** from [Google Fonts](https://fonts.google.com/), with category filters (serif, sans, display, handwriting, mono), a live sample, and a Use system reset. The previous system-font picker remains as fallback. Only **one chosen family** is loaded, not the entire library. The selected name is saved in versioned Chat presets, current edits, whole-editor JSON backups, and chat.html?gfont=... browser-source URLs. The emote wall is unaffected. A family name without a valid catalog match cannot be chosen from the picker.

**Local browser-source loading:** The loopback pnpm live server requests Google Fonts CSS2 and validated fonts.gstatic.com font assets and serves them through bounded, same-origin /api/fonts/css?family=... and /api/fonts/file/... routes. This avoids requiring OBS/Chromium's internal browser to contact Google directly; the desktop host still needs network access for a newly selected font. A cached family stylesheet and downloaded font binaries are held **in server memory**, with hard request/response size limits, bounded caches and a Google-only origin restriction. When the local route does not exist (e.g. preview-only `pnpm dev:vite`), the browser tries Google's stylesheet URL directly and falls back to the configured system font if no web font is available. The source uses font-display=swap. There are no bundled font files or API keys.

The ~95KB catalog snapshot is generated from Google Fonts' own https://fonts.google.com/metadata/fonts response, which is an **undocumented website metadata endpoint** (not the separately documented API-key-based Google Fonts Developer API). To update the bundled family list after new releases, run pnpm fonts:update, review its diff, and rebuild. It refuses unexpectedly small or malformed catalogs without overwriting the current snapshot. Selection currently loads each family's **default style**; per-family variable-font axes and full weight/italic controls are future additions rather than simulated.

**Usage:** choose the Chat overlay top tab, open Chat • Typography, search by name or filter category, click the desired family, and check the specimen and chat preview. Copy the Chat browser-source URL into OBS when ready. For already-running OBS sources, refresh the browser source to pick up the updated URL/font choice. Loading may take a moment on the first use; standard font fallback remains during loading.

## Chatbus capability contract (2026-10-18)

Chatbus is the **provider-normalization and identity source of truth**. Overlay Kit implements swappable visual consumers. Its normalized values are projected without serializing provider-specific raw payloads.

Third-party cosmetic lookups are best effort and may take longer than a message's display lifetime. A bounded resolver admits at most two active users with a maximum queued budget, coalesces repeated identities, caches normal results for five minutes and delays retries after failures. An external cosmetics API reaching a successful HTTP status does not prove any particular user actually has a badge or paint.

**Note:** the master **Display badges** switch and the per-type badge controls determine which display badges are rendered, not which provider APIs are queried. Chat can now reuse the sanitized name-paint layers as the whole message background as well as the username treatment; provider-specific visibility controls and further decorations can still build on the same normalized data contract without another provider parser.

## Architecture and next milestones

1. Chatbus owns platform connections and emote/provider normalization.
2. Admission/runtime owns deduplication, lifespan, capacity, clear and disposal.
3. Rendering is swappable for Stagehand, SketchyChat, alerts or other views.
4. Physics, GSAP, particles and custom effects own only their own animation layer and return disposal callbacks. One lifecycle owner per mounted item.
5. Preview/editor is distinct from OBS source output. A separate host supplies real events.

Next: native OBS CEF stress/profile run for chat motion with bursts, long wrapping messages and 50+ rows, verified Chatbus-to-localhost-to-OBS bridge with reconnect/moderation/security tests, credentialed live verification of the Twitch EventSub path, live 7TV entitlement invalidation, ChatIS-style color presets/bot filters, seeded effects replay, responsive safe zones and performance limits. Integrate the stable package into Stagehand only once its host interface is proven; Stagehand's current emote wall has overlapping engine lifecycles and unfinished preview/effect hooks.

## Static browser mode

`pnpm build:pages` produces `dist-pages/`, using relative paths suitable
for GitHub Pages project sites. The explicit browser-only capability uses
Chatbus's `./browser` entrypoint and the same transport-neutral live mixer
as the Node relay. The normal build preserves the existing local/hosted
server discovery. Browser mode never probes localhost from a public HTTPS page, and never shares provider credentials in source URLs. Chromium
verification at the Pages origin (local static assets, real upstream
network) joined Twitch and rendered an independent live chat message after
the editor closed. Kick discovery and direct Pusher public chat worked with a provider-issued
public descriptor; the normal realtime negotiation remains CORS-blocked.
Chatbus refreshes its static metadata through scheduled Pages builds, not a
chat relay. Native emotes and 7TV use existing browser provider APIs. Native OBS CEF and a deployed Pages origin are separate
verification boundaries.

The optional browser YouTube path uses the existing official Chatbus connector
with a caller-owned restricted API key, sent only in the Google API header.
The key is saved separately from editor settings in origin-local storage on
explicit user action. The browser's account panel and youtube-setup.html
provide masked input and a forget action. Source URLs and presets carry
only video IDs, never keys. One reader per editor/video forwards normalized
event/status/signal packets to its owning same-origin previews; independent
sources each retain their own reader. The ten-second minimum polling
interval, terminal quota/auth failure and cancellation tests protect user
quota. Public YouTube web endpoints remain blocked by CORS from Pages.
Live credentialed access has not been verified; the browser smoke uses
explicit Google API fixtures. The existing Node public reader is unchanged.

## Optional Vercel hosting

The public source is maintained at https://github.com/myrqyry/overlay-kit.
The following describes the optional hosted architecture, not a promise of
a currently available public service. Local self-hosting is supported independently.

Vercel serves the static editor and chat/wall browser sources, **plus a
hosted live Chatbus WebSocket function** at `/api/live` and an HTTP
capability endpoint at `/api/live/status`. The hosted studio lets you add
**Twitch**, **Kick**, **YouTube**, and **TikTok** sources to one selected set. That source
set is saved in your browser and included in shareable OBS URLs. Existing
single-source URLs remain compatible; mixed URLs use repeated
`source=<platform>:<channel-or-video-id>` parameters. A mixed browser source
opens one independent read-only WebSocket per selected provider room and merges
their normalized events only in that page; changing this studio does not
redirect someone else's source. Channels and concurrent connections are
bounded per function instance (three rooms and twelve clients by default).
A public relay remains subject to aggregate usage across Vercel instances.

Set `OVERLAY_TWITCH_CHANNEL` on the Vercel project to choose the initial
default channel if desired, and `OVERLAY_CHAT_PLATFORM=kick` if the
deployment itself should default to Kick. Otherwise
`server/hosted-channel.ts` uses Twitch + `xqc` only for URLs without an
explicit source. YouTube rooms require `OVERLAY_YOUTUBE_API_KEY` or
`OVERLAY_YOUTUBE_ACCESS_TOKEN` in the Vercel function environment; those
credentials never enter the generated browser-source URL. Selecting another
provider/channel requires no deployment. Visitor-selected sources are
normalized per provider and bounded as rooms keyed by `platform:channel`.
Public users cannot mutate *another room's* channel, send Chatbus control
packets, or disconnect anyone else's browser source. A generated OBS URL opens
its selected live streams directly, without requiring the editor to remain open.

The live-source button in the hosted editor is membership-aware: it **adds**
the current provider/target when absent and **removes** only that source when
already selected. Source chips expose the complete set with individual connection, emote and badge readiness and Reconnect / Disconnect actions. The embedded previews
and generated OBS URLs receive that whole set; each page owns and disposes its
own read-only room subscriptions. This is deliberately **not** a public,
server-wide disconnect: removing a source from this browser's selected set
does not redirect or disconnect another open OBS/browser source. Public room
ownership remains server-side and listener-scoped.

Removing the last hosted source now generates an explicit `live=0` URL
for every preview and generated browser source, closes the editor's own
room subscriptions, and saves an empty source list. Reloading the editor
does not restore the default channel after that explicit disconnect.
The default remains available for a first-time visitor with no saved
selection. Already-open independent OBS URLs retain their own source
subscriptions. In local mode, removing a source closes the provider
connection; the browser's idle status WebSocket can stay open.
See [disconnect regression evidence](docs/hosted-disconnect-2026-11-17.md).


The hosted function uses the real Chatbus Twitch/Kick/YouTube adapters (and TikTok unless explicitly disabled by the host) and
the existing normalized event pipeline. Twitch uses native badges and
identity/cosmetics enrichment; Kick uses Chatbus native subscriber badge
lookup, native message emotes and Kick-channel/global 7TV candidates; YouTube
uses the official Live Chat API path. Kick subscriber/gifter role refs remain
visible as bounded semantic `SUB N` / `GIFT N` badges when artwork is absent;
a resolved authentic subscriber milestone image replaces only the subscriber
fallback. Verified artwork for gifter and other legacy roles remains unresolved,
and YouTube-specific role/member artwork is not fabricated when Chatbus does
not supply it. Each Vercel Function instance owns provider rooms only while at
least one local WebSocket client is connected.
Different instances may each establish their own upstream connection; this is
intentionally not a globally durable pub/sub system. Fluid Compute limits and connection lifetime
apply, and clients automatically reconnect. Same-origin upgrade validation, normalized channel names, bounded room and
client counts, and read-only WebSockets constrain public access.
If you need externally mutable channels, private studio controls, or larger
concurrency, implement authenticated configuration and a durable room/relay
store rather than exposing the local unrestricted control endpoints.

Studio `preview=1` fixtures remain explicitly synthetic and are cleared
when a configured real live room is present. Local `pnpm live` uses the same
provider-aware hub. The hosted Twitch feed remains **anonymous IRC**, not
Twitch OAuth/EventSub. Kick uses Kick's anonymous web realtime negotiation,
not the authenticated official Public API. A successful socket upgrade alone
is never treated as message-delivery proof; provider status becomes connected
only after the transport's usable subscription state is confirmed.

If there is no usable default source, the hosted editor accepts a provider and
valid channel from the user. An empty or invalid selection never attempts a
connection.


Hosted Node Function sources live in `server/entries/`; `pnpm build` bundles
them with esbuild into reproducible `api/live.js` and `api/live/status.js`.
These generated entrypoints contain first-party code only; third-party npm
dependencies remain external and install from the frozen lockfile. They are
committed so Vercel's Function builder never loads extensionless TypeScript
imports or needs a sibling checkout. Don't
manually edit them; run `pnpm build` and review the generated diff.

The production build uses `vercel.json` (`dist-demo` Vite output),
`pnpm-workspace.yaml` (approved pinned esbuild install) and a tracked
`vendor/chatbus` runtime snapshot. See `vendor/chatbus/README.overlay.md`
and `UPSTREAM_COMMIT` before updating that snapshot. No private registry
token, sibling checkout, or local machine-specific path is needed by the
cloud build.

## Avatars (first playable slice)

Open **Avatars** in the studio or use the independent transparent OBS source at `avatars.html`. Real channel traffic comes from the existing Chatbus relay; the studio iframe uses explicitly synthetic preview messages. The first version draws procedural 2D characters (no downloaded skins or new rendering dependency). A viewer keeps one avatar across messages, autonomously wanders, rests, hops, and greets neighbors; an emote makes them hop and show its code briefly. User bans/timeouts remove their character; deleting a message removes its active thought bubble, not the viewer.

Avatars have independent population, character size, name visibility and calm/playful activity settings, exportable as source query parameters and presets. There is no 3D renderer, physics-engine collision, persistence across page reloads, custom skins or minigames yet. Browser source is empty until an event arrives; the studio preview is synthetic unless connected to live chat.

## Events — text notifications (first live slice)

The **Events** tab is a fourth independent editor workspace. Its transparent OBS browser source is `events.html`, and it subscribes to the already-forwarded Chatbus `SocialSignalV1` WebSocket packets—not to ordinary chat messages and not to an extra Twitch connection. It renders a bounded sequential queue of subscriptions, gift subscriptions, follows, raids, cheers, donations and reward redemptions **when those events are supplied by the real connection**. Event appearance, accent, typeface, entrance/exit effect and durations, placement and major event-category switches have independent validated settings and URL/preset state. **Type and tier overrides** let one event type—or one subscription tier such as Twitch 3, Prime, or a YouTube member level—replace those visual settings without changing the base configuration; see [Events type and tier overrides](docs/event-overrides.md). Unknown names, counts, tiers and subscription tenure are never guessed.

The existing anonymous Twitch IRC path can report subscription/gift and raid USERNOTICE events, but **not follow events**; follows require authorized EventSub scopes/connection and are only rendered if the social signal reaches the source. No new Twitch OAuth enrollment or full follower/subscriber database is implemented here. The editor previews use test-origin synthetic examples, isolated from ordinary OBS sources; clicking the sample button while Events is selected sends to the Events preview alone. The standalone `events.html` is initially empty until a supported live event arrives. Alerts use textContent (no HTML injection), deduplication, bounded display and exit timers, and a bounded wait queue. Each alert runs entrance → configured hold → exit even when no successor is queued; the next alert appears only after exit completion. A new event arriving during an exit waits its turn. Clear and dispose cancel timers and remove the card immediately. `eventMotion`/`eventMotionMs` and `eventExit`/`eventExitMs` persist through Events URLs and presets; reduced motion bypasses both entrances and exits. `eventAccent` and `eventFamily` restyle the existing card without changing event text or transport. Custom typed message templates, media/sounds and OBS-native performance validation remain future work.

## Local account sign-in (Chatbus OAuth, 2026-11-01)

Open **Platform accounts** from the person icon in the top-right toolbar. The panel explains each platform’s authorization and chat transport, and offers **Sign in / Sign out** through the local relay (`pnpm dev` or `pnpm live`). The OAuth protocol operations (`beginOAuth`, `exchangeOAuthCode`, `refreshOAuthToken`) belong to the pinned Chatbus snapshot; Overlay Kit owns callback state, restricted local token persistence and the account controls. **Hosted Vercel OAuth is not enabled:** its public account/session ownership still needs an authenticated backend. Hosted room chat continues to use its existing server environment credentials.

Register appropriate **web application** clients with the providers, including an exact redirect URI of `http://127.0.0.1:5219/api/oauth/callback` (adjust the port if configured), then start the local relay with:

```sh
OVERLAY_YOUTUBE_CLIENT_ID='...' OVERLAY_YOUTUBE_CLIENT_SECRET='...' \
OVERLAY_TWITCH_CLIENT_ID='...' OVERLAY_TWITCH_CLIENT_SECRET='...' pnpm live
```

Sign in is available only for configured services; linked accounts can be signed out. The panel distinguishes unavailable status, missing OAuth configuration, and signed-in state. TikTok does not use account authorization. Kick can now sign in through official Kick OAuth with S256 PKCE, using the local-only client credentials in the user's private `~/.config/chatbus/kick-app.json` (mode 0600); its registered callback is `http://localhost:5219/api/oauth/callback`. This enables the **account connection**, not an official realtime chat replacement. Kick chat still uses the existing anonymous web transport until a publicly reachable, signature-verified webhook implementation is available. See [Kick official API account and webhook boundary](docs/kick-official-oauth.md). Google requests `youtube.readonly`; Twitch requests `user:read:chat`. A connected YouTube account powers the official Live Chat API without copying an access token to an OBS URL. A connected Twitch account uses Chatbus's EventSub connector; otherwise Twitch keeps the previous anonymous IRC reader. Kick requests `user:read`, `channel:read` and `events:subscribe` but does not consume its user token for chat until official webhook delivery exists. Authenticate only with a provider account authorized for the desired channel and scope. Completing/disconnecting Twitch/YouTube authorization reconnects that provider's active sources; Kick authorization leaves its existing anonymous reader running.

The local account file `.oauth-accounts.json` is ignored by Git, written with permissions `0600`, and contains bearer/refresh tokens **in plaintext**. It is suitable only for a trusted single-user local machine with appropriate filesystem protection; it is *not* encrypted credential storage or a shared/public web-account system. Delete the account through **Sign out** before copying the workspace to another device. The OAuth callback rejects unsolicited/expired state, never places credentials in source URLs, and cannot be used on the public Vercel host. Refresh happens when the connection is established/re-established; this does not implement proactive mid-connection token rotation. Real provider sign-in and OBS CEF behavior still require credentialed manual verification.
